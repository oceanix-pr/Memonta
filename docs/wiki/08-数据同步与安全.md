# 08 · 数据同步与安全

[← 返回首页](Home.md) · 源码：Memonta/Services/FileSyncService.swift、CloudSyncService.swift、EncryptionService.swift

本篇覆盖数据可靠性与安全三件套：磁盘↔数据库双向同步、iCloud 状态、加密体系。

## 1. FileSyncService — 磁盘 → 数据库同步

源码：[FileSyncService.swift](../../Memonta/Services/FileSyncService.swift)

**设计哲学：文件系统是权威数据源**（每条录音/笔记一个 `yyyyMMddHHmmss[-N]` 文件夹），数据库只是索引。数据库损坏/换机时，全部记录可从磁盘重建。

### 1.1 主流程

```
扫描 ~/Documents/Memonta/ 子文件夹
  → 识别新文件夹（数据库中无对应 folderName 的记录）
  → readItemType(meta.json) 判定类型：recording / quicknote
  → 并发阶段：读取 meta.json + 探测音频时长（IO 密集，并行提速）
  → 串行阶段：逐条入库（共享同一 ModelContext，防交错）+ 保存数据库
```

### 1.2 关键方法

| 方法 | 职责 |
|------|------|
| 同步主流程 | 上述扫描-并发读-串行入库；崩溃遗留 PCM 分片（`*_mic_tmp_*.caf` / `*_sys_tmp_*.wav`）校验时长与音轨后恢复合并 |
| 快捷笔记同步 | 读加密/明文 `source.txt` 与 `source.png` → `EncryptionService.decryptFileOrPlaintext` → 文本加密入库 |
| `readItemType` | 读 meta.json 的 `itemType` 字段；`quicknote` 或"无音频但有笔记内容文件"（`hasQuickNoteContent`）判为笔记，否则按录音处理 |

### 1.3 触发时机与门控

- 启动任务链（RootView `LifecycleTasksModifier`，单 `.task` 内**串行**处理迁移、状态重置、磁盘对账与队列续跑，模型预热是唯一并行的独立任务；具体顺序见 RootView），用 `.task(id: 隐私同意状态)` 门控——用户同意隐私政策后才扫描用户数据
- 加密迁移分页保存并支持游标续跑；大循环定期 `Task.yield()` 保持 UI 响应

### 1.4 可靠性细节

- 新建条目文件夹用原子分配（`AudioRecording.createUniqueFolder(from:)`）：以 mkdir 成败为准，已存在则换名重试；「先查后建」在并发下会拿到同名，而旧 `createFolder` 对已存在目录也返回成功，两条记录会共用目录互相覆盖
- 扫描阶段并发读盘（可能持续数十秒），插入数据库前对 `folderName` 再做一次存在性检查（`fetchLimit = 1`），防止扫描期间用户导入/手动刷新插入同一文件夹导致重复条目
- 条目镜像（转写/总结/画面要点）统一走 `EntryMirrorStore`：同一目标的连续写入**合并为只写最新一份**，同一目标任意时刻只有一个写者；退出流程在拉起守护进程前 `flush()` 有界等待落盘。写失败经 `PersistenceReporting` 上报（旧实现是每处一个 `Task.detached` 一把火，刚保存完退出即丢最后一次修改）
- 已入库条目不再「完全跳过」：对账时双向补缺口——库里有内容而镜像缺失则补写镜像，镜像存在而库里为空则从磁盘补回库。只补缺失、不覆盖已有内容，正常条目只多一次 stat
- 后台任务队列（`.background_task_queue.json`）区分「文件不存在」与「文件损坏」：损坏时隔离为 `.corrupt-<时间戳>` 并尝试从 `.bak` 恢复，同时上报用户；拿不到跨进程 flock 时明确失败且**不写盘**（旧实现锁文件打不开就无锁执行、把损坏当空队列，会把全部待办任务覆盖掉）
- 文件夹名兼容 12/14 位时间戳格式（历史版本）；同秒冲突 `-N` 后缀解析前先剥离
- 旧版元数据（`title.txt`）回退兼容，新格式 `meta.json` 优先
- 原子写入 `data.write(to:options:.atomic)` 防元数据损坏

## 2. CloudSyncService — iCloud 同步状态

源码：[CloudSyncService.swift](../../Memonta/Services/CloudSyncService.swift)

**职责边界**：只做 iCloud 账户状态检查与"保存 → 同步中/成功/失败"状态反馈。**实际数据同步由 SwiftData+CloudKit 系统后台完成**——但注意 ModelContainer 中 `cloudKitDatabase: .automatic` 配置**当前被注释禁用**（待 CloudKit 容器配置完成后启用，需所有模型属性可选或有默认值）。

诚实反馈原则：无法得知真实同步结果时不伪造状态（不 sleep 后谎报"已同步"），CloudKit 未启用时只报"已保存到本地"。

## 3. EncryptionService — 加密服务

源码：[EncryptionService.swift](../../Memonta/Services/EncryptionService.swift)

### 3.1 算法与密钥

| 项 | 方案 |
|----|------|
| 算法 | CryptoKit **AES-GCM 256**（认证加密） |
| 密钥存储 | **Keychain**（`accessibility(.afterFirstUnlock)`） |
| 密钥创建 | 锁 + 双重检查 + **内存缓存**（防并发首次创建互相覆盖——旧密钥加密的数据将永久不可读；也避免每次加解密访问 Keychain） |
| 落盘策略 | 密钥落盘失败时报错，**绝不使用仅存内存的密钥** |

### 3.2 核心方法

| 方法 | 职责 |
|------|------|
| `encrypt(_:)` | 文本 → Base64 密文；失败报告并抛错，由调用方决定现有明文回退策略 |
| `decrypt(_:)` | Base64 密文 → 明文 |
| `decryptSafely(_:)` | **读路径兼容关键**：非 Base64 内容 = 明文回退，原样返回；仅 Base64 解密失败（损坏密文）才返回空。若统一返回空会静默清空明文数据并在下次保存时永久丢失 |
| `encryptAndWrite` / `decryptFileOrPlaintext` | 文件级加密写/兼容读（todos.json、ocr.txt、source.txt） |

### 3.3 加密数据清单

| 数据 | 位置 | 加密 |
|------|------|------|
| 转写片段文本 | SwiftData `TranscriptSegment.text` + transcript.json | ✅ |
| 录音总结 | SwiftData `AudioRecording.summary` | ✅（summary.md 为加密镜像） |
| 快捷笔记正文/OCR/总结 | SwiftData + 文件 | ✅ |
| 截图 OCR/纪要 | 图片型 QuickNote 字段 + 文件 | ✅ |
| AI 待办 | todos.json | ✅ |
| 截图图片 | PNG 文件 | ❌（原图/标注版不加密） |
| 录音音频 | m4a 文件 | ❌ |
| 导入的原始视频 | `{base}_video.mp4/mov/m4v` | ❌（与截图原图同一边界，仅本地留存；转写用的是抽出音轨，不是视频本体） |
| 画面要点 | SwiftData `visualSummary` + visual.md | ✅（与 summary 同一策略） |
| 抽出的关键帧 | `frames/kf_NN_秒s.jpg` | ❌（与图片类产物同一边界；帧里可能含他人屏幕与文档文字，重新分析时复用缓存） |
| API Key（Whisper/LLM） | Keychain（KeychainAccess 库） | 系统级 |
| AES 密钥本身 | Keychain | 系统级 |
| 导出的模型配置（含 API Key） | 用户选择的文件 | ✅ 与 §3.1 同一把**设备密钥**（`EncryptionService`）；密钥不出本机 ⇒ 仅本机可解（边界见 §3.5） |

### 3.4 一次性迁移

加密升级用 UserDefaults 标志 `encryption_migration_completed` 控制只跑一次；幂等判断用**真实解密尝试**而非格式启发式（见启动任务链）。

### 3.5 大模型配置导出的加密边界

导出走 `EncryptionService`（与 §3.1 同一把设备密钥，和转写/总结一致），**不向用户索取密码**：少一步操作，但换来一条硬边界 ——

- **只能在导出它的那台 Mac 上导入**。密钥存在本机 Keychain、不随文件走，所以文件拷到另一台 Mac 时导入会解密失败。实现上把这种情况与"文件损坏"分开提示（「该文件无法在本机解密：可能由其他 Mac 导出，或文件已损坏」），而不是含糊的「格式不正确」。
- 导入侧保留明文兼容：旧版未加密导出（不含 Key）仍可直接解析。判据沿用既有语义 —— 非 Base64 内容即明文（同 `decryptSafely` / `decryptFileOrPlaintext`）。注意导入用的是会抛错的 `decrypt(_:)` 而非 `decryptSafely(_:)`：后者会把"解不开的 Base64"记成解密失败并触发全局「密钥可能已更改」告警，而外来文件不该惊动本机数据。
- 明文负载（`LLMConfig.transferPayload` 的产物）含 API Key，只允许在内存中短暂存在，导出路径必须先加密再交给保存面板。

要跨 Mac 迁移又不想输密码，只有让密钥跟着 Apple ID 走（Keychain `synchronizable`）这一条干净路线；那会改变现有加密数据的安全模型，未采用。

## 4. 数据删除协议（安全删除顺序）

删除录音/笔记的统一顺序（RecordingViewModel）：

1. **先加载**依赖被删文件夹的侧数据（TodoDocument）→ 清理外部系统残留（提醒事项中已写入的 EKReminder）
2. **先删磁盘文件夹**，后删 DB 记录——文件删除失败时保留 DB 记录，防止下次磁盘同步"复活"
3. 删除确认对话框（单删/批删均弹）
